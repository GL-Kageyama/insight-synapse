# Insight Synapse
## Testing and Evaluation Framework Specification
### テスト・評価フレームワーク仕様書 v0.1（統合版）

> 旧版2ファイル（Test Strategy Specification / Testing and Evaluation Framework Specification）を統合した版。評価対象4階層とテスト対象レイヤーを包含。スコアは0〜1スケールに一本化。

---

# 1. 目的

本ドキュメントは、Insight Synapseの品質保証方法と評価基準を定義する。

目的：

> AIシステムの動作確認だけではなく、知的循環（判断・評価・改善）が成立しているかを検証する。

つまり、AIが「動くか」だけではなく、

> より良い判断・制作・改善ができているか

を測定する。

---

# 2. 基本テスト思想

一般的ソフトウェア：

```text
Input
↓
Process
↓
Output
↓
Correct?
```

Insight Synapse：

```text
Input
↓
Thinking
↓
Decision
↓
Action
↓
Evaluation
↓
Learning
↓
Improvement?
```

つまり、単純な出力正解判定ではなく、

「思考→判断→実行→評価→学習」

の循環が機能しているかを検証する。

---

# 3. 評価対象4階層

Insight Synapseでは、評価対象を4階層に分ける。

```text
Level 1
成果物
↓
Level 2
制作プロセス
↓
Level 3
思考・判断
↓
Level 4
システム進化能力
```

## 3.1 Level 1
## Artifact Evaluation

生成された成果物。

例：

- 文章
- コード
- 企画
- 設計
- 画像

評価項目：

```text
Quality
Logic
Creativity
Completeness
Usability
Value
```

## 3.2 Level 2
## Workflow Evaluation

制作プロセス。

評価：

- 不要工程がないか
- 必要工程が不足していないか
- 適切なSkill選択か

例：

```text
問題: 制作品質低下
↓
分析: Structure Phase不足
↓
改善: Workflow修正
```

## 3.3 Level 3
## Reasoning Evaluation

思考・判断品質。

評価項目：

- Problem Definition（問題設定能力）
- Exploration Quality（探索範囲）
- Decision Quality（判断妥当性）
- Risk Awareness（危険認識）
- Alternative Consideration（代替案検討）

## 3.4 Level 4
## Learning Evaluation

改善能力。

確認：

```text
経験
↓
分析
↓
改善
↓
次回性能向上
```

が発生しているか。

# 5. Primitive Test

## 目的

最小思考操作の品質確認。

対象：

- Decompose
- Compare
- Abstract
- Reframe
- Generate
- Evaluate

## 評価項目

### Accuracy

意図した変換ができるか。

### Consistency

同条件で大きく変化しないか。

### Explainability

処理理由を説明できるか。

例：

```text
Input:    複雑なサービス案
Primitive: Decompose
Expected: 機能 / 価値 / 対象ユーザー / リスク
```

---

# 6. Skill Test


```text

✓ 評価可能
✓ 再利用可能
```

# 8. Orchestrator Test

## 目的

判断エンジンの検証。

## Action Selection

適切な次行動を選択するか。

例：

```text

Unknown ↑
↓
Research
```

```text
未知度が低い場合:
Unknown ↓
↓
Creation
```

## Reason Test

判断理由を説明できるか。

悪い例：

```text

```

良い例：

```text

追加情報取得を優先します
```

# 13. 評価エンジン構造

```text
Evaluation Engine
├── Criteria Manager
├── Scoring Engine
├── Critic
├── Insight Extractor
└── Report Generator
```

## 13.1 Criteria Manager

評価基準管理。

保存：

```text
evaluation/
└── criteria.yaml
```

例：

```yaml
criteria:
  quality: 0.25
  logic: 0.20
  creativity: 0.20
  value: 0.25
  risk: 0.10
```

> **正版**：評価5軸の重み・overall算出式・合格しきい値の正版は `03_コアコンポーネント/00_数値定義書.md` §2。overall = quality×0.25 + logic×0.20 + creativity×0.20 + value×0.25 + (1−risk)×0.10。Riskのみ「低いほど良い」ため (1−risk) で評価に含める。

## 13.2 Scoring Engine

評価結果を数値化する。

例（0〜1スケール）：

```yaml
score:
  quality: 0.8
  logic: 0.7
  creativity: 0.9
```

## 13.3 Critic Layer

単純採点ではなく、改善点を発見する。

出力：

```markdown
Problem: 構造が弱い
Cause: 初期分析不足
Improvement: Explore Phase追加
```

## 13.4 Insight Extractor

評価結果から学習情報を抽出する。

入力：

- Score
- Critique
- Outcome

出力：

```markdown
Pattern: 複雑な課題では初期探索量を増やすと品質向上
```

# 14. Multi Evaluator設計

将来的には複数評価者を利用する。

```text
Quality Evaluator
+
Logic Evaluator
+
Creative Evaluator
+
Risk Evaluator
```

理由：

単一評価では偏るため。

## 評価者の独立性（自己評価の循環の遮断）

複数評価者を導入しても、すべてが同一系統のAIでは「AIがAIを評価する」循環が残る。評価の信頼性を担保するため、以下の独立性要件を課す。

```text
1. 盲検化
   評価者は成果物の条件（POCでは B0 / B1 / B2 / C1〜C4）を知らされずに採点する

2. 独立評価系統
   処理条件と同系列でない別系統の評価モデルを少なくとも1つ併用する

3. 人間較正サンプル
   人間が採点した較正サンプル（既定: 50件）で評価モデルのスコアを較正し、
   一致度（スピアマン相関・加重κ係数）を報告する
```

数値・較正の詳細は `03_コアコンポーネント/00_数値定義書.md` §2.6、POCプロトコルへの適用は `11_実装計画とロードマップ/09_最初の動く試作品設計書.md` §13 を正版とする。

> 較正サンプルの運用定義（サンプル構造・層別設計・人間評価者プロトコル・較正手順・構成概念妥当性の収束的/弁別的/既知グループ妥当性枠組み）は `03_コアコンポーネント/00_数値定義書.md` §2.6.1 を正版とする。

# 15. Regression Test

## 目的

改善による劣化防止。

対象：

- Workflow変更
- Skill変更
- Primitive変更
- Evaluation基準変更

確認：

```text
新バージョン
↓
過去ケース再実行
↓
品質比較
```

例：

```text
変更前: 品質 0.85
変更後: 品質 0.70
↓
変更を再検討
```

# 27. 最終定義

Insight Synapse Test Strategyとは、

> AIシステムの動作確認だけではなく、知的成長サイクルが成立しているかを検証するための品質保証体系である。

評価とは、

> AIを採点する仕組みではなく、AIを成長させるための知性そのもの

である。

最重要評価：

**「昨日より良い判断ができるようになっているか」**

を確認する。
