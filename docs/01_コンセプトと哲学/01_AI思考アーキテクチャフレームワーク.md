# Insight Synapse
## AI思考アーキテクチャフレームワーク
### 概要仕様書 v0.1

---

# 1. プロジェクト概要

## プロジェクト名

Insight Synapse

---

## コンセプト

Insight Synapseは、単に回答や成果物を生成するAIではなく、

**AI自身の思考状態・判断過程・評価・改善を管理するための思考アーキテクチャフレームワーク**

である。

中心となる考え方：

> AIの知能とは、答えを生成する能力だけではなく、目的に向けて状態を変化させ、思考方法そのものを改善する能力である。

---

# 2. 解決する問題

現在のAIエージェントは、多くの場合、

```text
目的
 ↓
AI推論
 ↓
ツール実行
 ↓
結果出力
```

という構造になっている。

しかし、この方式には以下の問題がある。

- 思考過程が再利用できない
- なぜその判断をしたか分からない
- 判断基準が固定されている
- 長期的な改善が難しい
- 人間が介入できるポイントが少ない

Insight Synapseでは、これらを解決するために、

**思考そのものを管理対象にする。**

---

# 3. 基本思想

## 3.1 思考 = 状態変化

Insight Synapseでは、思考を以下のように定義する。

```text
現在状態

↓

認知操作

↓

新しい状態
```

つまり、

思考とは単なる文章生成ではなく、

**状態をより目的達成に近づける変換処理**

である。

### 3.1.1 機能主義的前提の自覚

「思考 = 状態変化」は、Insight Synapseの出発点であり、同時に最も深い賭けである。この等式は定義ではなく、**作業仮説**である。

#### この前提が捉えられないもの

思考を状態遷移として扱うことで、以下の性質は原理的に外在化できない。

**身体化された思考（embodied cognition）**：
身体の感覚・運動・空間的接触を通じて生まれる思考は、状態遷移の記号列に還元できない。熟練した職人の「手が知っている」判断、演奏家の「身体が覚えている」フレーズ——これらは状態として記述された瞬間に、その固有の質を失う。

**発生的認知（enactive cognition）**：
環境との相互作用そのものが思考である場合、相互作用から切り離された「状態」は偽物である。対話の中で初めて形になる考えは、対話の外に取り出せば別物になる。

**質的意識（qualia）**：
「赤さ」の感じ、「痛み」の質——これらは状態遷移グラフのノードではない。意識の一人称的性質は、三人称的形式化の時点で消失する。

**暗黙知（tacit knowledge）**：
「言えるよりも多くのことを知っている」（Polanyi）。形式化できない知は、形式化を前提とするState Modelの外部にある。

#### 外在化で失われるもの

思考を形式化し、Traceとして記録し、評価可能にする——この一連の操作は、思考から以下のものを剥ぎ取る。

- **思考の内在的性質**：考えている最中の、まだ言葉になっていない手触り。それは形式化された瞬間に「かつての思考についての報告」に変質し、思考そのものではなくなる。
- **迷いの質**：State Modelは `unknown` を管理するが、`unknown` として明確化された迷いは、明確化される前の「何かがおかしいが何かは言えない」という状態とは別物である。形式化は迷いに名前を与えるが、名前を得た迷いは元の迷いではない。
- **過程の一回性**：Traceは思考経路を保存するが、保存された経路は「あのときの思考」の化石であり、生きた思考ではない。追体験は可能だが、同一の思考の再現は不可能である。

#### それでもこの前提を使う理由

上記の限界を認めた上で、なお「思考 = 状態変化」を採用する理由は一つである。

**この形式だけが、思考を他者と共有し、評価し、改善することを可能にする。**

形式化されない思考は、その本人だけのもので終わる。形式化は思考を殺すが、形式化を経なければ思考は他者に届かない。これは損失ではなく、**取引**である——内在的性質の喪失と引き換えに、共有可能性・検証可能性・改善可能性を得る。

Insight Synapseが賭けているのは、この取引が「損」ではないこと、すなわち形式化で失われるものより得られるものの方が大きいことである。だが、これは機能主義（心的状態は機能的状態である）が正しいという前提に立っている。機能主義が誤りであり、思考の本質が形式化不可能な質にあるならば、このフレームワーク全体が根拠を失う。

**Insight Synapseは、機能主義の正しさに賭けている。そして、その賭けの正否をPOC対照実験の実測で判定しようとしている。** これは二重の賭けである——形式化が有効であること、そしてその有効性を実証できること。この二つが同時に成立しなければ、この設計は成立しない。

> 本節はWisdom Council評価（v0.4-full）のphilosophical-evaluatorの指摘「計算主義的前提を一度疑う章を設けること」に応えるものである。設計の根底にある前提を自覚することは、設計の弱さではなく、設計の誠実さである。

## 3.2 責務分離

システムを以下に分離する。

```text
判断
↓
実行
↓
記憶
↓
評価
↓
改善
```

各レイヤーは明確な役割を持つ。

---

## 3.3 思考の軌跡を中心とした記憶

一般的なAIでは、

```text
知識保存
```

をMemoryの中心にする。

Insight Synapseでは、

```text
思考軌跡保存
```

を中心にする。

保存するもの：

- なぜその問いを作ったか
- なぜその判断を選択したか
- どの選択肢を捨てたか
- どの状態変化が起きたか

つまり、

**思考経路そのものを再利用可能な知識にする。**

---

## 3.4 なぜ人間が方向調整者なのか

この設計の最上流には、一つの人間観がある。**人間は作業者ではなく、方向調整者である。** これは修辞上の理想ではなく、次の三つの現実の物語がこの設計を要求しているからだ。

- **起業家・野村**——過去の失敗を恐れ、未知を確認せず蓋をする。「そのアイデアは、捨てなくてよかった」と思えるようになるには、AIが答えを押し付けるのではなく、判断の仕方を一緒に鍛えてくれる必要がある。
- **管理職・佐藤**——反対を押し切り失敗し、チームから諦められる。「反対が質問に変わる」には、判断理由が透明で、属人ではなく組織の言葉になる必要がある。
- **作家・鈴木**——結末を決めることを避け、書けなくなる。「直感はそのまま、思考だけが構造化される」には、迷いの正体を言語化する仕組みが必要である。

三人に共通するのは、求めているものが「答え」ではなく「**自分の判断力を取り戻すこと**」だという点である。以下に続くState・Orchestrator・Thought Trace・Evaluation・Learningの構造はすべて、この人間観を実現するための装置として配置される。

> この設計の構造的選択（unknown明示管理・Thought Trace中心の記憶・評価は改善のため・自己改善のLevel制約）は、いずれも「人間が方向を調整し続けられる」ことの必要条件である。構造は物語に従属し、物語は構造なしには実現しない。

> **物語の位置づけ（探索仮説）**：三人の物語が示す変化は、設計の「正当化」ではなく、**POCで実証すべき探索仮説**である。物語は現時点では成立しておらず、迷いが解消される保証もない。変化が本当に生じるかは対照実験（`11/09`）の結果で初めて分かる。物語はその探索の出発点であり、実証された成果ではない。

詳細な受益者物語は `08_データと技術仕様/03_ユースケース設計書.md` §14 を参照。

> 物語の心理的深度——野村の安堵と屈辱、佐藤の透明性と喪失、鈴木の解放と密室の喪失——は、`08_データと技術仕様/03_ユースケース設計書.md` §14 のv0.5改訂で深化された。この設計が人間に与える変化は、純粋な解決ではなく両面性を伴う。光と影の両方を描くことは、設計の誠実さの一部である。

Insight Synapseは、AIに以下の能力を持たせる。

---

## 理解能力

- 現在状態を把握する
- 未知部分を発見する

- 問いを生成する
- 仮説を作る
- 選択肢を比較する

- 再構成する

---

## 制作能力

- 成果物を生成する
- 改善する
- バージョン管理する

---

## 内省能力

- 判断を評価する
- 失敗理由を分析する
- 次回の戦略を改善する

# 8. 既存フレームワークとの差異

Insight Synapseは、既存の自己改善AI・エージェント・記憶管理手法の延長線上ではなく、**「思考そのものを管理対象・再利用対象にする」** 点で異なる。

## 比較

| フレームワーク | 中心思想 | Insight Synapseとの差異 |
|---|---|---|
| Reflexion | 失敗後に言語で振り返り、次の試行を改善 | 振り返りは改善ループの一部でしかない。State Model・unknown管理・思考経路の構造化保存を持たず、振り返りを「再利用可能な思考知識」として蓄積しない |
| Self-Refine | 同一生成内で feedback→improve を反復 | ループが単一タスク内で閉じる。タスクを跨ぐ長期記憶・判断基準の学習がなく、Orchestratorによる判断と実行の分離もない |
| MemGPT | コンテキスト窓を階層メモリで擬似的に拡張 | 目的は「記憶容量の拡張」。記憶を「思考経路の再利用」や「判断基準の改善」に使わず、Thought Traceを中心に置かない |
| Gödel machine | 自身のコードを数学的に証明付きで書き換える自己改善 | 理論上は完全だが実装困難。Insight SynapseはPOC対照実験（`11_実装計画とロードマップ/09_最初の動く試作品設計書.md`）による経験的検証と、人間承認（自己改善のLevel制約）による実践的自己改善を採用 |
| AutoGPT | 目的を分解しツールを自律実行 | 判断過程が暗黙的で、State・unknown・評価基準が構造化されない。評価→改善→学習の循環が第一級のレイヤーとして存在しない |

## 差異化の軸

Insight Synapseが既存手法に対して持つ4つの軸：

```text
軸1  思考 = 状態遷移 を明示的に扱う
     → State Model + unknown管理（未知を最重要情報にする）

軸2  思考経路そのものを再利用可能な知識にする
     → Thought Trace中心の記憶（「どう考えたか」を保存）

軸3  自己改善を「管理された改善」にする
     → 評価は改善のため・学習は制約付き・人間は方向調整者

軸4  差異化を「主張」ではなく「実測」で示す
     → Reflexion / Self-Refine との対照実験（N=20要因実験）で実証する
```

## 要点

> 既存手法は「出力を良くする」「記憶を増やす」「自律させる」ことを目指す。
>
> Insight Synapseは「AIの考え方そのものを、人間が監督できる形で改善し続ける」ことを目指す。

## 実証の位置づけ（重要）

上記の差異化は**現時点では設計上の主張であり、実測による検証を経るまでは未証明**である。

```text
検証手段　：POC対照実験（`11_実装計画とロードマップ/09_最初の動く試作品設計書.md`）
比較対象　：Reflexion / Self-Refine / Memoryなし（B0 / B1 / B2）
判定基準　：最良ベースライン比の成功率向上 ≥ 39pp で仮説Hの決定的支持
            20〜39pp は未確定帯域、5〜20pp は判定不能帯域
            → 両帯域は§12の事前登録ルールに従い追試（N=74/群以上・最大1回）で確定
            効果量・検出力の根拠は `11/09` §14、統計パラメータの正版は `03_コアコンポーネント/00_数値定義書.md` §8
```

設計文書としての完成度と、実証された価値は別物である。この文書群は前者を、POCは後者を担う。**次の成果物はこの文書の改訂ではなく、POCの実証結果である。**

# 10. 想定Runtime

## コア抽象とアダプタの分離

Runtimeは、コア抽象（State / Trace / Evaluation）を実装する**アダプタ**として位置づける。

```text
コア抽象：State Schema / Trace Schema / Evaluation Schema（Runtime非依存）

アダプタ　：Claude Code（第一実装）→ API Server → IDEプラグイン → Web UI
```

Claude Codeは唯一の実装ではなく最初のアダプタである。プラットフォーム側の機能吸収に備え、思考資産をRuntime非依存の形式で保持する。

## 第一アダプタ：Claude Code

理由：

- リポジトリ操作が可能
- Markdownとの相性が良い
- Gitによる履歴管理が可能
- Skillシステムを利用できる

# 11. 競争優位と収益モデル

## 競争優位の転換：概念から資産へ

競争優位は「思考管理という概念」ではなく、蓄積・再利用・相互運用できる**資産**に置く。

```text
概念（模倣可能）→ 資産（差別化可能）
  思考管理の思想     Thought Traceの標準フォーマット
                    + 蓄積した思考軌跡データ
                    + 評価・改善エンジン
```

概念は言語化されれば模倣される。Thought Traceの**標準フォーマット**と、そこに蓄積される思考データ、そして評価・学習エンジンの実装が、模倣困難な資産となる。

## Thought Trace 標準フォーマット提案

Thought Traceを業界の**標準フォーマット**として提案する。

```text
対象　　：YAML / JSON Schema（`05_メモリー/01` に定義）

狙い　　：AI評価・観測性市場における相互運用の共通言語

効果　　：
  - 異なるAIエージェント間で思考軌跡を交換可能にする
  - 評価ベンダー・観測性ツールが共通フォーマットで読める
  - 標準化により、自社のフォーマット定義そのものが市場での差異化になる
```

## 採用シナリオ（最初の採用者・初期市場）

標準フォーマットの普及は「誰が最初に使うか」から始まる。定義した最初の採用者（初期市場）は3セグメント。

```text
セグメント1：AI評価・観測性ベンダー
  　理由：思考軌跡を評価データとして扱う仕事をしており、共通フォーマットが
  　　　　自社評価の入力互換・比較可能性を高める。評価エンジンの精度で差別化できる。

セグメント2：オープンソースのAI観測性ツール（LLMトレース系）
  　理由：トレース出力に標準フォーマットを採用することで、エコシステム内の
  　　　　相互運用の要になりたい。シェア拡大の動機がフォーマット採用と一致する。

セグメント3：企業のAIガバナンス・監査チーム
  　理由：AI判断の透明性・監査ログを義務付けられている。ベンダー非依存の
  　　　　思考軌跡フォーマットは、監査対象の一元化・移行可能性を担保する。
```

最初の採用者の典型像（人間視点）は `08_データと技術仕様/03_ユースケース設計書.md` §14 に補足する。

## 標準化の戦略：実証後に広げる（standardize-after-prove）

Thought Trace標準フォーマットが「標準」になるのは、提案されたからではなく、**実証されたから**である。以下の段階的アプローチを取る。

### Phase 1：単一顧客への導入と実証（現在〜POC完了）

```text
単一の協力顧客（POCパートナー）にThought Traceを導入し、
実際の評価データで価値を実証する。

マイルストーン：
  - 実証済み評価レポート（実トレースデータに基づく改善事例）1件以上
  - 協力顧客からの継続利用意向の表明
  - POC対照実験の成功率データ（仮説Hの検証結果、11_実装計画とロードマップ/09）
```

この段階では、標準化の提案は行わない。フォーマットは「Insight Synapseの内部形式」であり、市場への公開資産ではない。最初の仕事は「誰かに使ってもらい、価値を測ること」である。

### Phase 2：オープンフォーマット化（実証後）

```text
Phase 1の実証データ（実トレース・成功率・改善事例）を携えて、
2社目・3社目の採用者にフォーマットを公開する。

マイルストーン：
  - Thought Trace YAML Schema の安定版（v1.0）公開
  - 採用企業3社以上（異なるセグメントから各1社以上）
  - Apache 2.0ライセンスでのSchema公開
```

フォーマットを公開するタイミングは、「規格を先に作る」ではなく「実績を先に作る」である。採用企業が「使いたい」と言った後に公開するのであって、公開してから「使ってほしい」と言うのではない。

### Phase 3：ネットワーク効果とデファクト標準化

```text
Phase 2の採用企業群が蓄積した相互運用データを基に、
フォーマットがデファクト標準として機能し始める。

マイルストーン：
  - 相互運用ネットワーク参加企業5社以上
  - 評価ベンダー・観測性ツールのフォーマット対応
  - 業界団体・標準化団体への提案（オプション）
```

### 標準化の逆説

標準フォーマットが成功する条件は、**標準化を急がないこと**である。急いで提案された標準は、実証の薄さゆえに採用されない。実証された形式は、提案せずとも採用される。

> Thought Traceフォーマットは「提案された標準」ではなく「実証された形式」として市場に入る。この順序の逆転（standardize-then-prove → prove-then-standardize）が、本戦略の中核である。

## 競争優位の再構成：データ独占からネットワーク効果へ

当初は「蓄積した思考軌跡データの独占」を競争優位の中心に置いていた。しかし、コア抽象をApache 2.0で公開する本モデルでは、**蓄積データは顧客側に残る**ため、「データの独占」は成立しない。競争優位は次のように再構成する。

```text
非独占（オープンコアが前提）　　独占（収益化の起点）
  Thought Traceの標準フォーマット  → 高度な評価・学習エンジン（商用ライセンス）
  State / Trace / Evaluation Schema  → ネットワーク効果の起点としての標準化
  蓄積データ（顧客側）              → SaaS（評価・改善ループをクラウド提供）
```

差別化の軸は「データの囲い込み」ではなく、**「標準の起点であること」+「標準の上で動く高度エンジン」** に移る。フォーマットが普及するほど相互運用ネットワークが広がり、その上で評価・学習エンジンとSaaSの需要が高まる。**ネットワーク効果がオープン化の代償を上回る**という設計が本モデルの骨子である。

## 収益モデル

```text
SaaS　　：AI評価・観測性プラットフォーム
         思考過程の可観測性・評価・改善ループをクラウドで提供
         価値＝「黒箱のAI」を「検証可能なAI」にする

ライセンス：
  - コア抽象（State / Trace / Evaluation Schema）はオープン（Apache 2.0）
  - 高度な評価・学習エンジンは商用ライセンス
```

オープンなコア抽象でフォーマット標準の普及（ネットワーク効果）を図り、高度エンジンとSaaSで収益化する。

> 収益モデルの前提（3セグメントの需要仮説）は、POC実行前の顧客発見インタビューと実行中の支払い意思検証（`11_実装計画とロードマップ/09_最初の動く試作品設計書.md` §15bis）によって実測される。セグメント列挙は実測前の仮説であり、実証された需要ではない。

# 14. 最終定義

Insight Synapseとは、

> AIが自身の状態を理解し、思考過程を記録し、判断を評価し、経験から考え方を自ら改善していくための認知アーキテクチャフレームワークである。

目的は、

「より速く答えるAI」

ではなく、

「考え方を自ら改善し続けるAI」

を作ることである。
