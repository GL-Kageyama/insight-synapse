# 1. 目的

本ドキュメントは、Insight Synapseの内部構造、各コンポーネントの責務、データフロー、実行モデルを定義する。

対象読者：

- Claude Code
- 開発AI
- 実装担当者

---

# 2. 基本アーキテクチャ思想

Insight Synapseは、単一の巨大AIではなく、

**状態管理・判断・実行・評価・改善を分離した認知システム**

として設計する。

基本ループ：

```text
Goal

↓

State認識

↓

判断

↓

実行

↓

評価

↓

改善

↓

次のState
```

### レイヤー境界（Runtime非依存）

上記のコンポーネントは、**コア抽象層（Runtime-Independent Core）** と **アダプタ層（Runtime Adapter Layer）** に分けられる。

```text
コア抽象層（Runtimeに依存しない）
  Workflow Engine / Orchestrator / State Engine / Evaluation Engine / Memory（Thought Trace）

アダプタ層（特定Runtimeに依存する）
  Claude Code Skill / ファイル操作 / Git操作 / API公開（最初のアダプタ実装は Claude Code）
```

コア抽象層はRuntimeを知らない。アダプタ層だけが特定Runtime（Claude Code等）の詳細に依存する。
この分離の詳細は §11 で定義する。

# 4. コンポーネント責務

---

## 4.1 Goal Layer

### 役割

AI活動の目的を定義する。

入力：

- ユーザー要求
- 制約条件
- 成功条件

出力：

Goal Object

例：

```yaml
goal:

objective:
"小説の第一章を作成"

constraints:

- 3000文字以内
- SF設定

success:

- 世界観の一貫性
```

---

## 4.2 Workflow Engine

### 役割

目的達成までの大きな流れを管理する。

担当：

- Workflow選択
- Phase管理
- 状態遷移

例：

```text
Creation Workflow

Question

↓

Concept

↓

Structure

↓

Create

↓

Evaluate
```

---

Workflowは固定処理ではない。

状態に応じて変更される。

---

## 4.3 Orchestrator

### 役割

現在状況から次のActionを決定する。

入力：

- State
- Workflow
- Policy
- Memory
- Evaluation

出力：

Next Action

例：

```yaml
action:

skill:
"question"

reason:

"目的が曖昧なため"
```

---

重要：

Orchestratorは生成を行わない。

判断専門。

---

## 4.4 State Engine

### 役割

AIの現在状態を管理する。

State例：

```yaml
state:

phase:
"exploration"

- AI設計思想

unknown:

- Runtime方式

confidence:
0.6

next_candidates:

- research
- prototype
```

---

Stateは常に更新される。

---

## 4.5 Skill Layer

### 役割

例：

Skillは組み合わせ可能。

## 4.6 Primitive Layer

### 役割

Skill内部で使用する最小思考操作。

例：

```text

抽象化

統合

```

構造：

```text

↓

↓

```

---

## 4.7 Artifact Layer

### 役割

実際の成果物生成。

対象：

- 文書

成果物とMemoryは分離する。

## 4.8 Evaluation Engine

### 役割

評価対象：

0.8

0.7

# 8. Runtimeアダプタ方針

## 基本方針

Claude Codeは実行基盤の**唯一の実装ではなく、最初のアダプタ実装**である。

コア抽象層（State / Trace / Evaluation）は特定Runtimeに依存せず、アダプタ層がRuntimeの詳細を吸収する。これにより、Claude Codeがプラットフォーム側で機能を吸収・終了しても、コア抽象と蓄積した思考資産は維持される。

## 第一アダプタ：Claude Code

```text
.claude/

commands/
人間操作

skills/
実行能力

agents/
役割定義
```

Claude Codeアダプタは、コア抽象層の情報を Markdown + YAML + Git にマッピングする。

## 将来のアダプタ例

```text
API Server（HTTPでコア抽象を公開）

IDEプラグイン（エディタ内でThought Traceを表示）

Web UI（人間が思考経路を閲覧・承認）
```

アダプタの追加・差し替えは、コア抽象層に変更を加えずに可能とする。

# 9. 設計上の重要判断

## 判断1

最初から完全自律化しない。

理由：

改善ループを確認できないため。

---

## 判断2

Memoryを後付けにしない。

理由：

思考履歴がLearningの入力になるため。

---

## 判断3

評価を独立層にする。

理由：

自己生成と自己評価を分離するため。

# 10. 最終アーキテクチャ定義

Insight Synapseは、

```text
目的
 ↓
状態理解
 ↓
判断
 ↓
思考操作
 ↓
制作
 ↓
評価
 ↓
改善
 ↓
経験化
```

という循環構造を持つ。

これは単なるAI Agent Frameworkではなく、

**AIの思考プロセスを設計・管理・改善する認知オペレーティングシステム**

として構築する。

# 11. コア抽象とアダプタの分離

## 背景

Claude Code単一依存は、プラットフォーム側が同等機能を吸収した場合の構造的リスクである。
このリスクのヘッジとして、**思考資産（State / Thought Trace / Evaluation結果）をRuntimeから独立させる**。

## コア抽象の3本柱

```text
State Schema      ：AIの現在状態の構造定義（正版：03_コアコンポーネント/01_状態モデル仕様書.md）

Trace Schema      ：Thought Traceの標準交換フォーマット（正版：05_メモリー/01 のYAML Schema）

Evaluation Schema ：評価5軸と算出式（正版：03_コアコンポーネント/00_数値定義書.md）
```

コア抽象は、特定のLLM・ツール・ファイル形式に依存せず、純粋なデータ構造として定義する。

## アダプタ層の責務

アダプタは、コア抽象と特定Runtimeの間の変換を担う。

```text
Claude Codeアダプタ
  コア抽象 ↔ Markdown / YAML / Git / Skill

APIアダプタ
  コア抽象 ↔ JSON / HTTP

IDEアダプタ
  コア抽象 ↔ エディタ表示・編集
```

## 依存方向の制約

```text
アダプタ層 → コア抽象層
```

逆方向の依存（コア抽象がアダプタの詳細を知る）は禁止する。これにより、コア抽象はアダプタを差し替えても不変である。

## 設計判断

- **判断1**：Claude Code固有の表現（SkillやCommand）をコア抽象に混ぜない
- **判断2**：蓄積したThought Traceは、Runtimeが変わっても読み替え可能な標準フォーマットで保存する
- **判断3**：アダプタの実装順は Claude Code → API → IDE とし、コア抽象の検証を優先する
